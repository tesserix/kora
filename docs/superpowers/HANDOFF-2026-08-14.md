## The #154 lesson — worth internalising

It "passed" twice on evidence that proved nothing.

1. **False pass.** Signed in with Apple, name visible in profile. But the DB showed one row with the
   same `firebase_uid` and a `created_at` from an earlier *Google* sign-in. Firebase had **linked the
   Apple provider to the existing Google account by matching email** — the console showed both
   provider icons on one identity. The name was Google-sourced.
2. **Still inconclusive.** Wiped the Kora `users` table and signed in again. Fresh row, name
   populated — but the same `firebase_uid`. Firebase Auth stores its own `displayName` on the user
   record, set earlier by Google, and that is what reaches `EnsureUser` in the token claim.
   **Wiping the application database does not isolate this**, because both the linking and the
   stored name live in Firebase, not Postgres. (This wipe was my suggestion and it was the wrong
   instrument.)
3. **Decisive.** Delete the Firebase identity AND revoke the Apple authorisation, then sign in. New
   `firebase_uid` **and** populated name — both conditions together. Either alone is what produced
   the two false results.

## Process that earned its keep — please keep doing this

**1. A green test proves nothing until you have seen it fail.** Three separate times this session:

- Two `AskAgainSheet` tests passed *with the guards deleted* — the mutation callbacks ran outside
  `act()`, so React never flushed and the assertions could not fail.
- `TestLocalDayRejectsGoZeroTime` used `INSERT ... SELECT FROM users LIMIT 1`, which inserts ZERO
  rows on an empty database. It passed locally and failed on CI — and **kept `build-image` skipped
  for five runs**, which is the real reason no image existed when a deploy was needed.
- `TestLocalDayBackfillMatchesProfileZoneForExistingRows` counted mismatches across `food_logs`, so
  on an empty DB it returned 0-of-0 and reported PASS while verifying nothing. It now skips.

Break the implementation, watch the test go red, restore. Every time.

**2. Run the suite against an EMPTY database.** `createdb`, `go run ./cmd/migrate`,
`TEST_DATABASE_URL=<scratch> go test -count=1 -p 1 ./...`. That is what CI does, and it is where
ambient-data assumptions surface.

**3. `-count=1` is mandatory after a schema change.** The Go test cache hid a real constraint
violation.

**4. Watch CI after every push.** Five red runs went unnoticed.

**5. Verify a deploy did what you think.** The first Redis sidecar deployed cleanly, went `2/2
Running`, and the cache was still disabled — Kubernetes starts regular containers in parallel and
kora-api probes Redis once at boot, so it lost a 3-second race. Only the pod logs showed it. The fix
was a native sidecar (`initContainer` + `restartPolicy: Always` + `startupProbe`).

**6. Check `git branch --show-current` before committing.** Work landed on the user's
`ci/advance-deploy-branch` by mistake and had to be cherry-picked off.

**7. Prefer a cheap local check to a slow remote one.** `sentry-cli info` caught a wrong region
config in seconds that would otherwise have cost a 15-minute build. Same for the lockfile
regeneration and the Redis eviction-policy test under Docker.

## Traps confirmed or discovered today

- **Never reintroduce `@react-native-firebase/*` or `useFrameworks`.** RNFirebase needs
  `useFrameworks` for SPM; under frameworks `react-native-screens` cannot import the private React
  header `React/RCTSurfaceTouchHandler.h` and the iOS build dies. Proven: #14/#15 green, Crashlytics
  commit, #16 red on that header, #18 green once both removed. `useFrameworks: "static"` is not an
  escape (expo/expo#39080). Firebase **auth** is fine — that is the JS SDK, no pods.
- **After ANY dependency change, regenerate the lockfile with
  `npx npm@10.9.3 install --package-lock-only`.** Local npm is 11.x, EAS runners use 10.9. Caught
  live: npm 11 omitted `@bacons/apple-targets/node_modules/typescript` and the remote `npm ci` would
  have failed.
- **Sentry:** do NOT set `SENTRY_URL`. Organization auth tokens embed their own region and
  `sentry-cli` prefers it. Org tokens have the fixed scope `org:ci` (`project:releases` is a
  personal-token scope). `@sentry/wizard` cannot run in the agent harness or via `!` (no TTY) and
  would add a second `Sentry.init` colliding with `src/observability/sentry.ts`.
- **The simulator cannot get past sign-in** without real credentials — there is no dev-auth bypass.
  To reach a signed-in screen, complete onboarding directly in the dev DB
  (`update users set ... onboarded_at=now()`).
- **`idb` synthetic taps do not drive the custom `ToggleSwitch`** (navigation Pressables are fine).
  Its a11y frames are content-space, so a control below the fold reports a y beyond the 874pt screen.
- Something in the harness **rewrote ASCII `''` to a smart quote `”`** in three Go comments between
  two commits. Restored in `5e89da9`; watch for it, since in a string literal it would be a real bug.

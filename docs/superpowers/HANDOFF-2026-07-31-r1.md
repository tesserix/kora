## The two CI failures, and why the original diagnosis was wrong

The previous handoff said CI was dead from a **GitHub billing block**. That was wrong on both counts:

1. **The `api` job** was failing because `weight_entries` was created **twice** — `000002_phase1_core` and again `000008_weight_entries`. Every *fresh* database died at migration 8 while already-migrated ones were fine, so it looked environmental. Verified against prod before fixing: prod is v17 clean and its table has `body_fat_pct`, proving `000002` is authoritative and `000008` never executed there. `000008` is now a documented no-op.
2. **`build-image`** then started running and failed at the push with `denied: permission_denied: write_package`. The GHCR package `tesserix/kora/kora-api` had **no repository linked** — it was first created by a manual laptop `docker push`, and an unlinked org package does not inherit the repo's Actions access, so no workflow-level permission could fix it. The user granted it in package settings.

**Prevention:** add `LABEL org.opencontainers.image.source=https://github.com/tesserix/kora` to `api/Dockerfile` so future pushes auto-link. Not done yet.

## ED-risk semantics changed — read this before touching the coach

`guardrails.AtRisk` gates the coach's eating-disorder protections. **Three of its four inputs treated absent data as evidence of risk**, so every brand-new user was flagged — and the coach UI renders that flag as an ED support card.

| Signal | Was | Now |
|---|---|---|
| `fastingStreak` | any zero-kcal day counted, from today | excludes today; requires prior logging; `LoggedBeforeWindow` keeps long silences visible |
| `recentDeficitPct` | unlogged days = 100% shortfall; today counted | excludes today; logged days only; minimum sample |
| `AvgIntakeKcal` | divided by a hard-coded 7 | excludes today; logged days only |

`guardrails.AtRisk`, its thresholds and the `Signals` struct are untouched — only the functions computing those inputs changed. `LogsPerDay` deliberately keeps `/7` (a per-calendar-day rate).

**This deliberately reduces sensitivity.** A flag that fires for everyone carries no information. The line drawn is *silence after established engagement*, not bare silence.

**Known remaining gap, filed not hidden:** a sporadic logger (e.g. logs only Mondays) is still flagged Thursday–Sunday every week by `fastingStreak`. The boundary case is fixed; the category error for users with *one* log in the window remains.

## In-app feedback (#61) — design note

Built against `tesserix/tickets-service` first. Checking the cluster showed **that service is deployed nowhere and used by nothing**, and that mark8ly — which is live — serves its own tickets from its own `marketplace-api` in a store-scoped table. The *pattern* was right (each product owns its table); the field names weren't. Realigned to mark8ly's live contract: `subject`, `description`, `status` (`open`/`in_progress`/`resolved`/`closed`), plus Kora's own `kind` (`bug`/`feature`).

Watch out: mark8ly's own zod schema comments `"pending"`, but its Go source uses `in_progress`. The Go source is the authority.

`support-platform` namespace is an AI/RAG assistant stack (Otto, embedder, reranker), not ticket CRUD.

## Process lessons worth keeping

- **Never `gh pr merge --delete-branch` on a PR with dependents.** Doing that on #58 deleted `kora-coach-thread`, which auto-closed #60 — and GitHub will not retarget or reopen a closed PR. Recovery: cherry-pick the branch's own commits onto the new `main` and open a replacement (#62). No commits were lost, but it cost a PR and its review history.
- **Never run two agents against the same checkout.** It happened once here; one agent's uncommitted work was also swept by a `git stash -u` from a branch switch. Use worktree isolation.
- **Verify, don't trust agent reports.** Multiple "done" reports needed correction. One break-it-to-prove-it attempt was itself wrong (reverting only a denominator left an early return intact, so the test still passed) — reverting the *whole* pre-fix behaviour was what actually proved the test load-bearing.
- Stacked PRs force migration numbers to be picked against the stack tip, not `main`. Flatten the stack promptly.

# Design — iOS home screen widgets (nutrition + steps)

**Date:** 2026-08-11
**Status:** approved, ready for planning

Two WidgetKit widgets on the iOS home screen: one showing today's calories and
macros, one showing today's step count. Small and medium sizes. Tapping either
deep links into the matching screen.

## Why

Kora's two most-checked numbers — calories remaining and steps — both require
opening the app. A home screen widget removes that step for the glance, which
is most of the daily interaction with a food tracker.

## Goals

- Nutrition widget: calories remaining against target, plus macros at medium size.
- Steps widget: today's steps against goal, updating through the day without
  the app being opened.
- Small and medium, home screen only.
- Tap deep links to the relevant screen.

## Non-goals

Explicitly out of scope, and addable later without rework:

- Lock screen accessory widgets.
- Interactive widgets (App Intents, quick-log buttons).
- Android widgets.
- Any widget-initiated write. The widgets are read-only surfaces.

## Constraints discovered before designing

These three findings shaped every decision below.

**1. `ios/` is gitignored (`apps/mobile/.gitignore:42`).** The app uses Expo
Continuous Native Generation: the Xcode project is regenerated by
`expo prebuild`. Adding a widget target by hand in Xcode would be silently
wiped on the next prebuild. The target must be produced by a config plugin,
with its Swift sources tracked in the repo.

**2. HealthKit is already integrated.** `src/health/useHealth.ts` reads
`HKQuantityTypeIdentifierStepCount` (goal 10,000) and sleep analysis;
`ios/Kora/Kora.entitlements` already carries `com.apple.developer.healthkit`
and `.background-delivery`. The step widget is a display problem, not an
integration one.

**3. There is no App Group yet,** and exactly one native target. Both need to
change.

## Approach

`@bacons/apple-targets` (v5.0.0, published 2026-07-17, peer `expo >=52`; this
app is on `expo ~57.0.8`) generates the WidgetKit extension during prebuild
from sources tracked in the repo.

Two alternatives were considered and rejected:

- **Hand-rolled config plugin** manipulating the `pbxproj` directly. No
  third-party build dependency, but pbxproj manipulation is brittle and this
  reimplements the chosen plugin with more code and less testing.
- **Abandon CNG** — commit `ios/` and manage Xcode by hand. Conceptually
  simplest for widgets, but it is a one-way door affecting the whole app: every
  future Expo SDK upgrade becomes a manual native merge. A permanent, app-wide
  cost for a single feature's convenience.

The accepted risk of the chosen approach is a single-maintainer package sitting
in the build path.

## Architecture

```
apps/mobile/
  targets/kora-widgets/
    expo-target.config.js     target type, entitlements, deployment target
    KoraWidgets.swift         @main WidgetBundle
    NutritionWidget.swift     small + medium
    StepsWidget.swift         small + medium
    Snapshot.swift            Codable snapshot + staleness rule
  modules/widget-bridge/      local Expo module (app side)
```

App Group `group.com.tesserix.kora` is added to **both** the app target and the
widget target. The widget target additionally carries the HealthKit
entitlement.

## Data flow

### Nutrition — snapshot, pushed by the app

The widget does not call the API. The auth token lives in the app's own
storage, and sharing it through a Keychain access group would widen the
security surface for no benefit the snapshot does not already provide.

1. On a successful dashboard fetch, the app serialises the current day to JSON:
   `{ date, kcalConsumed, kcalTarget, protein, carbs, fat }` (each macro
   carrying consumed and target).
2. `widget-bridge` writes that JSON into the App Group `UserDefaults` and calls
   `WidgetCenter.shared.reloadAllTimelines()`.
3. The widget's `TimelineProvider` reads and decodes the snapshot.

Because the app pushes the reload, logging a meal updates the widget within
seconds. Nothing polls.

### Steps — read live from HealthKit

`StepsWidget` queries HealthKit directly: an `HKStatisticsQuery` summing
`stepCount` from local midnight to now. This is what makes the count climb
through the day without the app being opened.

A widget extension **cannot request** HealthKit authorization — there is no UI
in which to present the prompt. It reads only what the app has already been
granted, and renders a "connect" state otherwise.

iOS budgets widget refreshes (roughly tens per day), so the count is near-live,
not live. The provider returns a single entry with
`.after(now + 15 minutes)`: frequent enough that a walk shows up within a
quarter hour, sparse enough to stay inside the daily budget. iOS treats that as
a request, not a guarantee, and may refresh later than asked.

## States

| State | Nutrition | Steps |
|---|---|---|
| Normal | kcal left (small); kcal + macros (medium) | steps + goal ring |
| No snapshot yet | "Open Kora" | n/a |
| Snapshot stale (date ≠ today) | treated as absent → "Open Kora" | n/a — read is live |
| Health not authorised | n/a | "Connect Health in Kora" |
| HealthKit read fails / unavailable | n/a | "—" with goal still shown |

Two of these rows encode decisions worth keeping:

**Staleness is the sharpest correctness risk.** If the widget wakes at 00:05
and the newest snapshot is yesterday's, rendering it would present *yesterday's
calories as today's*. The snapshot therefore carries its `date`, and
`Snapshot.swift` treats any snapshot whose date is not today as absent. This is
the same invariant the food log enforces around `logged_at`: a figure must
describe the day it claims to.

**An unknown step count is never rendered as 0.** Zero steps and "we could not
read your steps" are different facts. The widget shows "—" for the latter.

**Logout clears the snapshot.** Otherwise the home screen keeps showing the
previous user's calorie data after sign-out, visible without the app open and
with nothing to explain it. `widget-bridge.clear()` is called from the same
path that tears down the session.

## Deep links

Via `widgetURL`, reusing the existing `mobile://` scheme (verified working
2026-08-11 via `mobile:///log`):

- Nutrition widget → `mobile:///diary` (`app/(tabs)/diary.tsx`)
- Steps widget → `mobile:///progress` (`app/(tabs)/progress.tsx`)

Both are tab routes in the `(tabs)` group, so the group segment does not appear
in the URL. Each link is asserted by a test that resolves it against the router,
so a future rename cannot silently break a home screen tap — nothing else in the
app would fail if these strings went stale.

## Testing

**Covered by jest, on the TypeScript side:**

- Snapshot serialisation from `DashboardSummary`: shape, rounding, date stamping.
- Write-on-dashboard-refresh, including that a *failed* fetch does not overwrite
  a good snapshot with nulls.
- Clear-on-logout.
- The native module is mocked at the boundary, following the pattern
  `src/health/__tests__/useHealth.test.tsx` already uses for HealthKit.

**Not covered, stated plainly:** the Swift side has no automated tests.
WidgetKit views resist unit testing, and adding an Xcode test target through a
config plugin is more machinery than this feature earns. The mitigation is to
keep Swift dumb: `Snapshot.swift` holds the only real logic — decode plus the
staleness comparison — and the widgets are near-pure rendering.

The staleness rule is the piece most deserving of a test and will not have one.
Moving that decision into TypeScript was considered: the app would write `null`
once the day rolls over. It was rejected because it only fires while the app is
open, so the widget still needs its own guard for the overnight case — which is
precisely the case that matters.

**Manual verification on the simulator** (iPhone 17 Pro, per project
convention): both widgets, both sizes, plus the empty and unauthorised states.

## Risks

- **Build-path dependency** on `@bacons/apple-targets`. Mitigated by the Swift
  sources being ours and portable: if the plugin is abandoned, the same files
  can be wired by a hand-rolled plugin or by committing `ios/`.
- **Untested Swift logic**, above.
- **Widget refresh budget** is controlled by iOS, not by us. "Near-live" means
  minutes, not seconds, and cannot be promised more precisely.
- **First prebuild after adding the plugin** regenerates `ios/`; any local
  uncommitted native state is lost. This is already true of the repo today.

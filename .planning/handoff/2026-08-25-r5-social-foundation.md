## The single most important thing

**#326 shipped a permission model that has no user interface.** Circles can only
be created by calling the API directly. The three open R5 issues are, in
dependency order:

1. **#153** — find friends from contacts. Circle membership is constrained to
   accepted friendships (`share.Service.AddMember` returns `ErrNotFriends`), so
   circles are only as useful as your ability to find people. Today that means
   friend codes and typing an exact signup email.
2. **#438** — a cross-user read path for body metrics. `access.CategoryBody` is
   defined and enforced and **consumed by nothing**. A `body` toggle shipped
   before this would be a setting that shares data no path returns.
3. **#437** — the Circles UI: settings, the named-people confirmation on
   granting `body`, the per-category audit view.

#437 can ship `progress`-only surfaces without #438. It cannot honestly ship a
`body` toggle without it.

## Decisions already made — do not relitigate

- **Circles, not per-person grants.** Visibility is (viewer, category). The
  settings screen and the audit view both stay O(circles), not O(friends).
- **Grants are one-directional.** A circle belongs to its owner and exposes only
  that owner's data. Sharing with your spouse never implies the reverse.
- **`access.NewService` takes the CONCRETE `Repository`, deliberately.** An
  unexported Go interface does NOT prevent external structural satisfaction — a
  substituted granter could otherwise forge permission. There is a scratch-file
  compile error proving it in the task record. Do not "simplify" it to an
  interface; the doc comment says why.
- **`share.Service.friendSource` stays an interface** even though the above went
  concrete. Different trade: it only decides who may be ADDED to a circle, and a
  concrete type would force a `share` → `social` import. Documented in code.
- **`ErrNotShared` / `ErrNotOwner` render 404, never 403.** A 403 confirms the
  thing exists and is withheld.
- **`ErrNotShared` has no handler mapping yet.** `Resolve` (singular) has zero
  production callers; the first handler to use it and forward the error gets a
  **500**. #438 must add the mapping and an HTTP-level test.
- **Challenges do NOT consult grants.** Joining a challenge IS the consent there.
  A comment above `standingsFor` says so and warns against unifying it — doing so
  empties existing leaderboards.
- **`share.Service.Leave` is not owner-gated.** That is its purpose. The handler
  is the only guard and must take the member id from the authenticated caller
  alone, never request input.
- **Export returns your own data only** (#24). Another person's readable metrics
  are not yours to export.

## Repo traps

Everything in the previous handoff still applies. New and expensive:

- **The Go module root is `api/`, not the repo root.** `go test ./api/internal/...`
  fails with "cannot find main module". Always `cd api && go test ./internal/<pkg>/`.
- **npm version skew will waste an hour.** CI runs node 22.19.0 which bundles
  **npm 10.9.9**; a modern local machine has npm 11. A lockfile generated by
  npm 11 is rejected by npm 10 with `Missing: typescript@5.9.3 from lock file`
  — a symptom that points nowhere near the cause. Regenerate with
  `npx npm@10.9.9 install --package-lock-only`.
- **`build-image` needs the aggregate `CI gate`**, which needs `[api, mobile,
  secrets]`. So a mobile dependency advisory blocks the Go API image and every
  deploy. This cost a full day. Meanwhile `ios-release.yml` depends on CI not at
  all — the mobile checks gate the artifact they have nothing to do with and not
  the one they do. Worth its own issue.
- **Editor/gopls diagnostics lie constantly**, especially in a git worktree
  outside the gopls workspace — they report `BrokenImport` on files that build
  fine. Trust `go build` and `go test` only.
- **Test Postgres is on 5433**, and DB suites need `-p 1`.

## Working practices the user expects

- **Mutation-check every test that guards something.** Make the change that
  should break it, watch it fail, restore. This plan found **seven tests passing
  against deliberately broken implementations** — including one guarding a
  privilege-escalation path, and one that hid a blocker through nine consecutive
  reviews. The implementations were nearly always correct; the evidence was not.
- **Verify an issue's premises before planning off it.** #153's four code claims
  were checked and all held — which is unusual here and worth the five minutes.
- **Say what is not verified**, on every PR, in its own section.
- **Read every CI step, not the job's colour.** Merging past a red gate on the
  assumption that "it's the usual failure" put a real regression on `main` for
  hours (#428).
